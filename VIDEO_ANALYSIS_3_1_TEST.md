# Алгоритм анализа видео — 3.1-test

Статус: отдельная тестовая линия, `SHADOW_ONLY`.

Базовая версия: **3.1 FREE**. Ревизия тестовой линии: `3.1-test-r3`.

`3.1-test` не заменяет 3.1 FREE, не активируется автоматически и не имеет права
самостоятельно публиковать результаты в Канон школы, production-базу или профиль
ученика. Его задача — собрать в одном воспроизводимом контуре все последние
дополнения, проверить их на реальных видео и только после отдельного аудита
предлагать изменения стабильной версии.

## 1. Назначение

3.1-test превращает запись занятия по спортивному бриджу в единый тестовый
evidence-пакет и мастер-анализ. Он наследует методическую основу 3.1 FREE и
добавляет новые технические каналы: runtime-attestation, строгую проверку
результата, анонимное разделение спикеров, карточный shadow-challenger,
ориентацию стола, речевые указания карт и метаданные сдачи.

Главный результат одного запуска — один мастер-PDF. Внутри PDF хранится человекочитаемый полный анализ и встроенный `master_analysis.json` с теми же данными в машиночитаемом виде.

## 2. Неприкосновенность исходника

Исходное видео:
- не переименовывается;
- не перемещается;
- не удаляется;
- права доступа исходника не изменяются;
- фиксируются Drive ID, имя, MIME, размер, длительность, SHA-256, родительская папка и матрица доступа;
- после формирования результата исходник повторно проверяется на идентичность.

Неизвестные данные не достраиваются по догадке. Используется `UNKNOWN`/`UNCERTAIN`.

## 3. Основные педагогические принципы

1. Качество решения оценивается по информации, которой игрок располагал в момент решения, а не по результату конкретной сдачи.
2. Правильный ответ с неправильным рассуждением может считаться ошибкой.
3. При диагностике ошибки в первую очередь различаются:
   - отсутствие знания правила;
   - знание правила без распознавания ситуации;
   - неправильное рассуждение.
4. Системность ошибки оценивается по повторяемости и контексту, с учётом уровня игрока.
5. Для новичков приоритет — простота и рабочий алгоритм; исключения не перегружают объяснение.
6. Для продвинутых игроков акцент может смещаться на исключения, альтернативы и стилистические решения.
7. В индивидуальном занятии ошибка может быть сознательно оставлена до конца раздачи, чтобы последствия усилили обучение. Это не должно автоматически считаться пропуском преподавателя.
8. Тема не считается закрытой навсегда: если ошибка возвращается, тема снова поднимается в приоритете.
9. Факты, выводы, рекомендации и неопределённость хранятся раздельно.

## 4. Конвейер

### 4.1. Идентификация занятия

Создаётся устойчивый `job_id`, зависящий от источника, а не от версии алгоритма. Определяются паспорт записи, участники (только если надёжно извлечены), тип занятия, дата и другие доступные метаданные.

### 4.2. Поиск готовой транскрипции

В родительской папке видео сначала ищется готовая транскрипция Zoom (`VTT`/`SRT`). Если она содержит таймкоды и проходит независимый аудио-QC, она становится основным транскриптом.

Если готовой надёжной транскрипции нет — запускается локальный Whisper на бесплатном GitHub-hosted runner.

### 4.3. ASR и таймкоды

Техническая обработка аудио может идти окнами, но итоговый транскрипт хранится на уровне реальных речевых сегментов Whisper/Zoom с глобальными таймкодами. Пятиминутные ASR-окна никогда не являются педагогическими границами эпизодов.

### 4.4. Автономный акустический QC транскрипции

Проверяются:
- начало;
- середина;
- конец;
- равномерная выборка;
- все окна с бриджевыми терминами.

Проверка выполняется повторным независимым распознаванием. При неудаче используется повтор без строгого VAD. Ненадёжные сегменты помечаются и не используются как твёрдые факты.

Важно: высокая похожесть двух распознаваний не доказывает правильность бриджевого смысла. Два прохода ASR могут одинаково ошибиться в термине.

### 4.4.1. Семантический QC бриджевой речи

После акустического QC выполняется отдельный пост-ASR проход по бриджевому языку. Он введён после анализа реальных ошибок расшифровки вроде `паз → пас`, `12 тысячков → 12 очков`, `туск-роль → туз-король`, `двойной паспорт → двойной импас`, `минуле → миноре`, `валед → валет`, искажений `3БК`, `гейм`, названий мастей и бескозырных контрактов.

Правила слоя:
- сырой ASR никогда не уничтожается и сохраняется в `raw_text`;
- для дальнейшего анализа создаётся отдельный `analysis_text`/`normalized_text`;
- каждая автоматическая коррекция сохраняет исходный фрагмент, замену, правило, confidence и причину;
- узкие, многократно наблюдавшиеся фонетические ошибки могут исправляться автоматически;
- неоднозначные варианты не исправляются молча, а сохраняются как `UNRESOLVED_CANDIDATE`;
- особенно критичны исправления, способные изменить бриджевый смысл: пас/контра, масть, уровень заявки, БК, фигура, количество очков, контракт и техника розыгрыша;
- неразрешённая критическая коррекция не может автоматически стать `FACT`;
- fuzzy-сопоставление со словарём используется только как подсказка и само по себе ничего не переписывает;
- словарь и ASR prompt пополняются реальными терминами школы: `3БК`, `инвит`, `туз-король`, `двойной импас`, названия мастей и фигур, `фоска`, `синглет`, `ренонс` и др.;
- статус транскрипта отдельно показывает результат акустического QC и семантического QC.

Таким образом, конвейер различает три уровня:
`сырой звук → сырой ASR → семантически нормализованный транскрипт → педагогический анализ`.

### 4.5. Визуальный проход 1

Всё видео сканируется на изменения сцен и perceptual hash. Формируется карта визуальных событий.

### 4.6. Визуальный проход 2

Извлекаются полноразмерные необрезанные кадры в:
- визуальных изменениях;
- речевых эпизодах с важной бриджевой терминологией;
- начале/конце;
- других критических точках.

Скриншоты выбираются по педагогической значимости, а не ради равномерного интервала.

### 4.7. Синхронизация текста и изображения

Каждый смысловой эпизод связывается с ближайшими релевантными кадрами и сегментами транскрипта. Любой важный вывод должен иметь доказательную основу: таймкод, речь, кадр или сочетание.

### 4.8. Семантическая сегментация

Занятие делится по смыслу, а не по техническим блокам. Возможные типы:
- объяснение;
- вопрос/обсуждение;
- торговля;
- розыгрыш;
- защита;
- ошибка/коррекция;
- методический эпизод;
- переход темы;
- новая сдача.

Каждый эпизод получает устойчивый `episode_id`.

### 4.9. Реконструкция сдач

Для каждого игрового эпизода создаётся `deal_id`. Пытаемся восстановить только подтверждаемые данные:
- четыре руки;
- торговлю;
- контракт;
- разыгрывающего;
- первый ход;
- ход розыгрыша;
- результат.

Если данных недостаточно — поле остаётся `UNKNOWN`. Допустимо вычислить четвёртую руку из трёх полных рук, если это явно фиксируется как вычисление.

### 4.10. Анализ решений

Для значимого решения создаётся `decision_id` и по возможности фиксируются:
- игрок;
- доступная ему информация;
- действие;
- проговорённое рассуждение;
- оценка качества решения;
- альтернативы;
- связь результата сдачи с решением.

Результат одной сдачи не является критерием правильности решения.

### 4.11. Диагностика ошибок

Ошибка не хранится просто как «неправильно». Выделяются причина, тема, уровень уверенности, повторяемость и педагогический приоритет.

Базовая диагностика:
- правило не известно;
- правило известно, но ситуация не распознана;
- неправильная логика рассуждения;
- другие категории добавляются по мере анализа реальных занятий.

### 4.12. Правильные решения и прогресс

Собираются также:
- хорошее рассуждение;
- самостоятельное применение правила;
- перенос знания в новую ситуацию;
- улучшение относительно прошлых занятий.

Профиль ученика не должен быть только списком ошибок.

### 4.13. Анализ преподавателя

Максимально подробно фиксируются:
- что объяснялось;
- способ объяснения;
- вопросы;
- аналогии;
- примеры;
- немедленная и отложенная коррекция;
- реакция учеников;
- качество и точность объяснения;
- соответствие уровню;
- перегруз исключениями;
- темп;
- места, которые можно улучшить.

### 4.14. Отложенная коррекция

Последовательность «ошибка ученика → преподаватель не вмешивается → проявляются последствия → разбор в конце» должна быть распознана как возможный педагогический приём, а не автоматически как пропущенная ошибка преподавателя.

### 4.15. Библиотека лучших объяснений

Удачные эпизоды становятся кандидатами в библиотеку:
- тема;
- таймкод;
- формулировка;
- аналогия;
- пример;
- контекст;
- реакция учеников;
- почему объяснение оказалось полезным.

После анализа большого массива видео строится профиль преподавательского стиля.

### 4.16. Канон школы

Нормативная проверка идёт в порядке:
1. канонические материалы школы;
2. накопленная база школы;
3. внешние источники — на последующих этапах обработки.

В мастер-анализе различаются:
- подтверждает канон;
- дополняет;
- альтернативный подход;
- противоречие;
- пробел.

### 4.17. Пробелы канона

Если в занятии возникает значимый вопрос без ответа в каноне, создаётся `knowledge_gap`. Он должен позже пройти процесс:
- поиск в базе;
- поиск внешних вариантов;
- сравнение подходов;
- рекомендация;
- подготовленный вопрос преподавателю;
- утверждение/отклонение/изменение канона.

### 4.18. Профиль ученика

Когда личность надёжно установлена, обновляются:
- пройденные темы;
- текущие навыки;
- сильные стороны;
- ошибки;
- повторяющиеся проблемы;
- прогресс;
- домашние задания;
- темы для повторения;
- рекомендации.

Уровень навыка многомерный; общий ярлык «начинающий/продвинутый» недостаточен.

### 4.19. Профиль группы

Объединяются повторяющиеся затруднения нескольких игроков. Для продолжающих групп профиль группы может определять тему следующего занятия вместо жёсткого курса.

### 4.20. Рекомендации

Мастер-анализ может формировать:
- тему следующего занятия;
- упражнения;
- учебные сдачи;
- домашнее задание;
- темы, которые нужно перепроверить;
- методические улучшения преподавателя.

### 4.21. Типы утверждений

Каждая существенная запись должна быть одной из:
- `FACT` — подтверждено источником;
- `INFERENCE` — аналитический вывод;
- `RECOMMENDATION` — предложение;
- `UNCERTAIN` — данных недостаточно.

Инференс нельзя автоматически повышать до факта.

## 5. Мастер-файл

Один мастер-PDF содержит:
1. паспорт;
2. краткую карту занятия;
3. хронологию;
4. подробные смысловые эпизоды;
5. полноразмерные значимые кадры;
6. восстановленные сдачи;
7. решения игроков;
8. ошибки и сильные решения;
9. анализ преподавателя;
10. кандидатов в библиотеку лучших объяснений;
11. связь с каноном;
12. пробелы;
13. профили/обновления профилей;
14. рекомендации;
15. полный нормализованный транскрипт с таймкодами;
16. сырой ASR и журнал семантических коррекций внутри `master_analysis.json`;
17. акустический и семантический QC;
18. встроенный `master_analysis.json`.

Все производные материалы строятся из мастер-файла, а не повторным разбором исходного видео без необходимости.

## 6. Качество результата

Технический успех и качество содержания — разные понятия. Успешный ASR/PDF не означает качественный педагогический анализ.

В `content_quality` отдельно фиксируются:
- количество сегментов транскрипта;
- смысловых эпизодов;
- визуальных доказательств;
- кандидатов ошибок;
- преподавательских наблюдений;
- кандидатов лучших объяснений;
- найденных связей с каноном;
- пробелов;
- кандидатов сдач и решений;
- количество автоматических семантических коррекций;
- количество критических коррекций;
- количество неразрешённых семантических кандидатов;
- количество неразрешённых критических кандидатов;
- предупреждения о неполном семантическом покрытии.

## 7. FREE-ограничение

Производственный 3.1 FREE не использует платные AI/API или платные облачные вычислительные fallback-механизмы. Допустимы стандартные бесплатные GitHub-hosted runners, локальные модели и бесплатные операции Google Drive в пределах существующей инфраструктуры.

## 8. Развитие алгоритма

Схема мастер-анализа стабильнее конкретных эвристик. По мере анализа сотен и тысяч записей можно улучшать:
- словарь и список реальных ASR-ошибок;
- семантическую нормализацию;
- контекстную проверку заявок, мастей, фигур, контрактов и чисел;
- распознавание говорящих;
- реконструкцию сдач;
- классификацию ошибок;
- оценку педагогического эффекта;
- профиль преподавательского стиля;
- персональные профили;
- генерацию следующего занятия.

Стабильная производственная версия остаётся **3.1 FREE**. Отдельное имя
**3.1-test** используется только для изолированного испытательного профиля.


## Редакция 3.1-free-r25.8 — достоверность результата и подтверждённое самоулучшение

r25.8 сохраняет защиту r25.7 от повторной тяжёлой обработки и добавляет обязательный контракт качества:

- запрошенная и фактическая модель Whisper должны совпадать; производственный режим использует `medium`;
- `NO_SPEECH` разрешён только при явно пустой основной расшифровке и подтверждающих контрольных признаках;
- производные результаты не содержат e-mail, имён и идентификаторов пользователей;
- отдельно считаются кандидаты и содержательно заполненные сдачи, решения и учебные циклы;
- результат маркируется `FULL`, `PARTIAL` или `ARCHIVE_ONLY`;
- слабые и повторяющиеся связи с каноническим конспектом не считаются подтверждёнными;
- `KNOWLEDGE_APPLIED` создаётся только после фактической записи в базу; при пропуске или отсутствии конфигурации фиксируется `KNOWLEDGE_NOT_APPLIED`;
- ранний `CLEANUP_ACK` по-прежнему завершает повторный запуск до загрузки видео и ASR.

Постоянное правило: техническое завершение, педагогическая полнота и фактическое применение знаний — разные состояния и публикуются раздельно.

## 9. Состав 3.1-test и последние дополнения

В тестовую линию включены следующие изменения последнего цикла разработки:

1. **Universal Video runtime** с ограниченным контрактом задания, лимитами
   длительности/размера и устойчивым `job_id`.
2. **Runtime-attestation v2**: отдельно фиксируются установленный commit и
   commit, реально наблюдавшийся при выполнении задания. Их несовпадение
   блокирует доказательство результата.
3. **Evidence-export** только для одного заранее указанного завершённого job:
   без запуска видео, ASR, Oracle или записи в Drive.
4. **Строгая conformance-проверка**: повторно проверяются manifest, JSONL,
   таймкоды, QC, кадры, хеши, speaker-report, deferred-стадии и набор артефактов.
5. **Анонимная структура спикеров v2** с защитой от схлопывания кластеров,
   реальных имён, изменения текста ASR и сохранения непроверенных меток.
6. **Profiled Card Challenger v2** для распознавания карт в shadow-режиме.
7. **OCR-канал достоинства и масти** с отбрасыванием неполных или
   низкоуверенных пар.
8. **Независимый full-card канал**: составленная карта должна согласовываться
   с отдельным эталоном полной карты.
9. **Регистрация кадра и повороты** 0°, 90°, 180°, 270°.
10. **Проверенный порядок карт интерфейса** и позиционирование по сторонам.
11. **Прямое речевое обозначение карты** преподавателем или учеником с разными
    уровнями доказательной силы.
12. **Номер сдачи, дилер и зональность** с проверкой стандартных циклов
    дубликатного бриджа.
13. **Консенсус независимых кадров**, защита от повторного подсчёта одного и
    того же файла и конфликтов одной карты в разных руках.
14. **Вывод четвёртой руки из 39 карт** только при полном бесконфликтном наборе.
15. **Пошаговый аудит после каждого видео** до решения о следующем запуске.
16. **Раздельная матрица готовности**: техническое выполнение, ASR, спикеры,
    ключевые кадры, карточный анализ, DDS3, педагогика и публикация получают
    независимые статусы.
17. **Строгий учёт стадий**: выполненная стадия не может одновременно попасть в
    `deferred_analysis`; producer и verifier используют один расчёт.

## 10. Исполняемый профиль

Имя профиля: `bridge_lesson_3_1_test`.

Пример задания находится в
`examples/video_algorithm_3_1_test_job.json`. Профиль запускается только при
явном указании этого имени; наличие файлов, переменных среды или старых
артефактов не может включить его автоматически.

План стадий:

1. `media_preflight`;
2. `audio_extract`;
3. `transcribe`;
4. `transcript_qc`;
5. `timeline`;
6. `algorithm_manifest`;
7. `keyframes`;
8. `speaker_structure`;
9. `bridge_context`;
10. `bridge_positions`;
11. `dds3_optional`;
12. `educational_candidates`;
13. `package`.

Каждый результат содержит файл `algorithm_3_1_test.json`, в котором перечислены
версия, ревизия, исходный commit, все возможности и обязательные gates. Хеш
этого файла записывается в result manifest и пересчитывается независимым
verifier.

В `3.1-test-r3` manifest также содержит `readiness` со статусом каждой
плановой стадии. Пока `bridge_context`, `bridge_positions`, `dds3_optional` и
`educational_candidates` реально не исполнены, `content_result` равен
`ARCHIVE_ONLY`, а `publication_readiness` — `BLOCKED_SHADOW_ONLY`. Техническое
`COMPLETED` означает только успешное завершение технического контура.

## 11. Алгоритм разделения спикеров

1. Исходный текст ASR и его таймкоды копируются без изменений.
2. Опциональный diarizer возвращает только аннотации к тем же сегментам.
3. Любое расхождение количества сегментов, изменение текста, нечисловой или
   бесконечный confidence, неизвестный статус либо более восьми голосов даёт
   `INCONCLUSIVE`.
4. Требуются минимум два реально наблюдаемых кластера; один кластер считается
   риском схлопывания.
5. Все исходные метки повторно переименовываются в `SPEAKER_A…SPEAKER_H`.
6. При любом отказе все speaker-поля удаляются из транскрипта.
7. `teacher/student` — только кандидат роли. Реальные имена не присваиваются.
8. Не сохраняются аудио, voice embeddings и межурочные голосовые профили.
9. Отдельный verifier заново пересчитывает labels, counts, privacy и связь с
   transcript.
10. В профиле `bridge_lesson_3_1_test` положительный speaker-result требует
    разметки не менее 80% сегментов транскрипта и не менее 80% длительности
    речи. Два найденных кластера на небольшой части длинного урока больше не
    дают ложный `PASS`.
11. При покрытии ниже порога все speaker-поля удаляются, результат получает
    `INCONCLUSIVE / INSUFFICIENT_LABEL_COVERAGE`.

Порог 80% относится только к тестовому профилю и записывается в хешируемый
`algorithm_3_1_test.json`. Стабильный `bridge_lesson` сохраняет прежний
`speaker-structure-v1` без изменения контракта.

Положительный технический результат диаризации не доказывает личность человека.

## 12. Алгоритм распознавания карт

### 12.1. Профиль интерфейса

Перед распознаванием требуется human-verified профиль конкретного интерфейса:
эталонный кадр, размеры, геометрия стола, все rank/suit templates, все 52
full-card templates, их SHA-256 и общий template-set hash. Неполный,
изменённый или неутверждённый профиль блокируется.

Если утверждённого профиля и pixel-backend нет, стадия возвращает
`UNAVAILABLE`. Это означает «распознавание не выполнялось», а не «распознано
ноль карт».

### 12.2. Раскладка и стороны

Для подтверждённого школьного интерфейса используется порядок мастей:

- сверху и снизу по горизонтали слева направо: черва, трефа, бубна, пика;
- слева и справа по вертикали сверху вниз: черва, трефа, бубна, пика;
- внутри масти карты идут по убыванию от туза к двойке.

Экран может быть повёрнут на 0°, 90°, 180° или 270°. Сначала карта относится к
экранной стороне `top/right/bottom/left`, затем проверенный rotation-profile
переводит её в логическую сторону `N/E/S/W`. Сам recognizer не имеет права
назначить сторону напрямую.

Порядок мастей и карт используется только как `LAYOUT_SUGGESTION`: он помогает
разрешить неоднозначность, но сам по себе не создаёт наблюдаемую карту и не
участвует в выводе четвёртой руки.

Раскладка записывается в machine-readable definition: `H,C,D,S`; оси
`top/bottom = LEFT_TO_RIGHT`, `left/right = TOP_TO_BOTTOM`; допустимые повороты
— только `0/90/180/270`. Изменение любого поля меняет SHA-256 definition и
блокируется verifier.

### 12.3. Визуальное подтверждение

Для принятой карты одновременно требуются:

- валидная регистрация кадра и homography;
- rank и suit из одного glyph-канала;
- отдельное совпадение с full-card reference из другого канала;
- согласие обоих каналов по карте;
- confidence каждого канала выше утверждённого порога;
- геометрически определённая рука;
- минимум два разных SHA-256 кадра с тем же `card + seat`;
- отсутствие этой карты в другой руке.

Повтор одного файла не повышает поддержку. Конфликт даёт `CONFLICT`, а не
выбор «наиболее вероятной» руки.

### 12.4. Речевое подтверждение

Прямое называние карты учитывается вместе с визуальным evidence:

- нормализованная и точно привязанная реплика преподавателя может стать
  shadow-наблюдением только при подтверждённой роли/личности, достаточном
  speaker confidence, declaration confidence и связи с кадром/таймлайном;
- реплика ученика сохраняется как `STUDENT_SPEECH_SUGGESTION`: она может
  подтвердить, опровергнуть или поддержать layout-кандидат, но не имеет права
  самостоятельно добавить карту, завершить сдачу или запустить `39 → 13`;
- сомнительная, перекрывающаяся или неатрибутированная речь остаётся
  `UNCERTAIN`.

## 13. Номер сдачи, дилер и зональность

Номер сдачи принимается только как confidence-gated observation с локатором
кадра и консенсусом независимых кадров. Строка вида `board-7`, используемая как
идентификатор трека, не считается распознанным номером сдачи.

После подтверждения номера дилер и зональность вычисляются по стандартным
циклам 4/16 сдач. Если на экране отдельно прочитаны дилер или зональность, они
обязаны совпасть с вычисленным циклом. Несовпадение блокирует метаданные сдачи.

## 14. Реконструкция и доказательный статус

Карты разных эпизодов объединяются только по устойчивой идентичности сдачи:
подтверждённому номеру или другому проверенному visual anchor. Близость по
времени не является ключом сдачи.

Типы результата:

- `OBSERVED` — непосредственно подтверждено evidence;
- `DERIVED` — вычислено детерминированно из полного подтверждённого набора;
- `SUGGESTION` — подсказка, не используемая как факт;
- `CONFLICT` — противоречивые доказательства;
- `UNAVAILABLE` — стадия не могла быть выполнена;
- `INCONCLUSIVE` — стадия выполнена, но доказательств недостаточно.

Четвёртая рука выводится только при ровно 39 уникальных подтверждённых картах,
по 13 в трёх руках, без дубликатов и конфликтов. Вывод помечается `DERIVED` и
не становится Каноном автоматически.

## 15. Evidence, аудит и запрет promotion

Для каждого теста сохраняются:

- запрос и точный `job_id`;
- source fingerprint и контрольные суммы;
- installed/observed runtime commit;
- ASR/QC и speaker-report;
- manifest кадров и их SHA-256;
- shadow JSONL карт и summary;
- rejection/conflict reasons;
- `canonical_promotion_allowed=false`;
- итог conformance-verifier;
- результат ручной контрольной выборки.

После каждого видео выполняется цикл:

`прогон → независимая проверка evidence → измерение ошибок → bounded-исправление → regression → решение GO/NO-GO для следующего видео`.

Следующее видео не запускается автоматически. Для текущей очереди после
«Дианы 13» действует отдельное правило: «Диану 14» не запускать без новой
явной команды.

## 16. Матрица готовности r3

| Контур | Возможные статусы в тесте | Текущая граница |
| --- | --- | --- |
| Техническое выполнение | `COMPLETED` / `REVIEW` | Не доказывает содержание |
| ASR | `PASS` / `REVIEW` | Сырой текст и QC обязательны |
| Спикеры | `PASS` / `INCONCLUSIVE` | Только анонимные кластеры |
| Ключевые кадры | `PASS` | Не означает распознавание карт |
| Бриджевый контекст | `DEFERRED` | Семантический модуль не подключён к runner |
| Карты и позиции | `DEFERRED` | Нет утверждённого pixel-backend/profile |
| DDS3 | `DEFERRED` | Не запускается без доказанной позиции |
| Педагогика | `DEFERRED` | Не публикуется из одного ASR |
| Публикация | `BLOCKED_SHADOW_ONLY` | Канон и production неизменяемы |
| Итог содержания | `ARCHIVE_ONLY` | Пока нет исполненного бриджевого и педагогического слоя |

Producer записывает `stage_outcomes` для всех плановых стадий. Verifier строит
ту же матрицу заново и отклоняет bundle при расхождении, включая попытку
объявить `bridge_positions=PASS` без карточных доказательств.

## 17. Критерии выхода из test

Для возможного переноса отдельных компонентов в стабильную линию требуются:

- реальный независимо версионированный pixel-backend;
- утверждённый и hash-bound interface-profile;
- замороженный human-verified holdout на разных видео и поворотах;
- точность `card + seat` не ниже утверждённого порога;
- ноль ошибок стороны, дубликатов и ложных полных сдач;
- подтверждённая защита приватности спикеров;
- воспроизводимый runtime-attestation и полный evidence bundle;
- независимая проверка не ниже I2;
- отдельное решение о promotion.

До выполнения всех критериев единственный допустимый режим —
`TEST / SHADOW_ONLY / canonical_promotion_allowed=false`.
