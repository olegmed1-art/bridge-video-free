# Дополнение к алгоритму DDS Learning v2.3: безопасный запуск и доказательства

Это дополнение является обязательной частью
`ALGORITHM_DDS_LEARNING_V2_3_RU.md`. При противоречии старого примера запуска с
этим документом действует данное дополнение.

## 1. Запрет прямого DDS-запуска

Команда вида

```text
run_stage.py evaluate --start
```

не является внешним интерфейсом. Она допустима только как внутренний дочерний
процесс `authorized_run_stage.py` после атомарного потребления одноразовой
квитанции.

`sitecustomize.py` проверяет это ещё до импорта `run_stage.py`. Отсутствие
квитанции, неправильный scope, commit, event или marker завершает процесс до
загрузки вычислительного алгоритма.

## 2. Что связывает квитанция

Квитанция `dds-launch-authorization-v1` одновременно связывает:

- репозиторий;
- ветку/ref;
- точный commit SHA;
- GitHub actor и triggering actor;
- `workflow_dispatch`;
- scope (`main_train`, `validation`, `sealed_test` и др.);
- SHA-256 task manifest;
- SHA-256 высокоэнтропийного nonce;
- время выдачи и срок действия;
- точную фразу явного подтверждения.

Квитанция действует не более 60 минут и может быть потреблена ровно один раз.
Retry требует новой явной авторизации.

## 3. Отдельная авторизация каждой фазы

TRAIN, derived, validation и sealed test имеют разные scopes. Разрешение TRAIN
не открывает validation. Разрешение validation не открывает sealed test.

Для sealed test wrapper автоматически добавляет `--open-sealed`; для любого
другого scope этот флаг недоступен.

## 4. Архив завершённого пилота

Workflow пилота 10 000 переведены в архивный no-op:

- они не содержат `run_stage.py`;
- не содержат `--start` или `--open-sealed`;
- не имеют push/schedule-триггера;
- не могут повторно открыть прежний sealed test.

Исторические результаты пилота сохраняются неизменными.

## 5. Воспроизводимость solver

Используются:

- DDS commit `37c8a79f4c67c55d1a309ccb66dd00cb58af464a`;
- Bazel 7.6.1;
- Bazelisk 1.29.0;
- Python ABI cp314.

Bazelisk принимается только после SHA-256 сверки официального release asset.
DDS HEAD сверяется с закреплённым commit. Wheel-cache принимается только при
совпадении wheel SHA, DDS commit, ABI и хеша bootstrap.

## 6. Доказательство тёплого кэша

Heavy CI выполняет повторный bootstrap после удаления venv и исходного build.
Второй запуск выполняется с `DDS_REQUIRE_WHEEL_CACHE=1` и обязан восстановить
проверенный wheel без компиляции. Иначе интеграционный тест проваливается.

## 7. Полнота файлового аудита

Проверяются и tracked, и untracked-файлы. Расширение не имеет значения:
обнаруживаются PBN, SQLite, бинарные и extensionless-файлы. Разрешены только
явные runtime-каталоги.

## 8. Фактическое покрытие

`test_matrix.json` остаётся реестром, но больше не считается доказательством
покрытия сам по себе. Во время suite `coverage_runtime.py` собирает фактически
исполненные строки и переходы во всех дочерних Python-процессах.

`coverage_report.py` сопоставляет реальные данные с производственными модулями,
считает line coverage, исполненные arcs и наблюдавшиеся branch sites и применяет
минимальные пороги, закреплённые в manifest.

## 9. Запрет плавающих CI-зависимостей

Все `actions/*` в DDS-workflow закрепляются полными commit SHA. Checkout не
сохраняет credentials. Тестовые workflow имеют только read-доступ.

## 10. Статусы готовности

После этих изменений статус может быть повышен только раздельно:

- тестовая архитектура — после зелёных fast и DDS suites;
- main TRAIN readiness — после чистой репетиции 30 000 и успешного launch guard;
- holdout — только после фактической OOF-калибровки TRAIN;
- stable skill — только после контрпримеров, подтверждённого правила и
  real-world transfer;
- интеграция в основную ветку — только после чистого переноса на актуальный
  `main`, повторных тестов и обязательных checks.

Ни один зелёный технический тест сам по себе не является заявлением о
приобретённом бриджевом навыке.
