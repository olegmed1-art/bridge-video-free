# Политика хранения, изменения и удаления данных — v1.0

Дата вступления в силу: 2026-08-18
Статус: CANONICAL POLICY CANDIDATE — действует после merge в `main`
Область: весь проект «Школа спортивного бриджа», включая GitHub, GitHub Actions, Google Drive, Neon PostgreSQL, Vercel, DDS, видеообработку, учебные материалы, отчёты, recovery и служебные артефакты.

## 1. Приоритет и отмена устаревших правил

Эта политика заменяет и отменяет прежнее общее правило «ничего не удалять без команды пользователя» в той части, где оно запрещало безопасное автоматическое удаление технических, временных, дублирующих и уже надёжно перенесённых данных.

Сохраняется усиленное правило для оригиналов и уникальных данных: исходники, уникальные материалы пользователя, канонические знания и данные, которые невозможно полностью восстановить, не удаляются без прямой команды владельца.

Если старое правило, инструкция, workflow или документ противоречит этой политике, действует эта политика, кроме более строгих правил безопасности, защиты оригиналов, production-recovery и teacher-authority.

## 2. Классы данных

### P0 — Оригиналы и невосполнимые данные

Примеры: исходные видео и аудио, книги, документы пользователя, оригинальные PBN/турнирные данные, записи занятий, исходные изображения, материалы преподавателя.

Правила:
- оригинал не изменяется обработчиком;
- обработка выполняется на копии или производной версии;
- автоматическое удаление запрещено;
- удаление допускается только по прямой команде владельца;
- перенос допустим только без потери доступности, идентичности и provenance; до подтверждения нового места старое не удаляется.

### P1 — Канонические знания и системная история

Примеры: утверждённая методика, правила торговли, teacher decisions, provenance, correction/regression evidence, применённые миграции, идентичности алгоритмов/версий, audit history.

Правила:
- история не переписывается задним числом;
- изменение выполняется новой версией, forward-fix или новой записью;
- старое состояние получает статус `superseded`, `deprecated`, `quarantined`, `rejected` или иной явный статус;
- автоматическое физическое удаление запрещено, если оно разрушает историю решений или аудит.

### P2 — Данные воспроизводимости и восстановления

Примеры: milestone state, corpus identity, manifest, обученные модели, release/recovery snapshots, подтверждённые checkpoints крупных этапов.

Правила:
- долговременное файловое хранение по умолчанию — Google Drive;
- Neon хранит идентичность, checksum, provenance, status и location;
- GitHub Actions может хранить временную рабочую копию;
- старую копию можно удалить только после появления проверенной замены и после завершения периода, когда она нужна для recovery/rollback.

### P3 — Полезные производные результаты

Примеры: PDF-анализы, презентации, учебные материалы, статистические отчёты, итоговые выгрузки.

Правила:
- долговременное хранение — Google Drive;
- существенные версии должны быть идентифицируемыми и воспроизводимыми;
- точные дубликаты могут удаляться автоматически после проверки основной копии;
- опубликованный/выданный ученику результат не должен молча перезаписываться новым содержимым под той же версией.

### P4 — Рабочее состояние процесса

Примеры: restart/resume state незавершённого run, shard progress, временные intermediate datasets.

Правила:
- хранится там, где это нужно для процесса;
- защищается от удаления до завершения или безопасного checkpoint;
- после завершения нужный milestone повышается до P2/P3, остальное может удаляться автоматически.

### P5 — Кэши и воспроизводимые технические данные

Примеры: GitHub Actions cache, build cache, скачанные зависимости, компиляционные каталоги.

Правила:
- не являются архивом;
- могут удаляться автоматически;
- постоянная копия не требуется, если данные детерминированно или практически восстановимы;
- сохранение допускается только ради производительности/стоимости запуска.

### P6 — Логи и диагностика

Примеры: CI logs, debug logs, runtime diagnostics.

Правила:
- важные выводы, root cause и regression evidence сохраняются отдельно в P1/P2;
- исходные технические логи могут иметь ограниченный retention;
- секреты, DSN, токены и персональные данные не должны сохраняться в логах;
- лог нельзя считать единственной копией критического evidence.

### P7 — Точные дубликаты

Примеры: две копии одного и того же файла с тем же checksum.

Правила:
- дубликат определяется по содержимому/checksum, а не по имени;
- лишняя копия может удаляться автоматически после прохождения Deletion Gate;
- наличие разных storage providers может быть намеренной redundancy и не считается лишним дубликатом, если это предусмотрено recovery policy.

## 3. Основная модель хранения

### Google Drive
Основное долговременное файловое хранилище для P0, P2 и P3, а также для крупных файлов, которые нет необходимости постоянно держать в GitHub Actions.

### Neon PostgreSQL
System of record для метаданных и связей: идентичность, checksum, provenance, version/status, location, verification, run linkage, correction/regression/recovery evidence. Большие бинарные файлы в Neon не хранятся без отдельного обоснования.

### GitHub repository
Основное хранилище исходного кода, workflow, тестов, текстовых архитектурных политик, миграций и версионируемой технической документации.

### GitHub Actions
Рабочая среда и временное техническое хранилище. Не является долговременным архивом проекта. Всё, что можно безопасно хранить на Google Drive без ухудшения качества, скорости, restart/resume, recovery или воспроизводимости, после verification должно быть освобождено из Actions либо иметь минимально разумный retention.

### Vercel / runtime filesystem
Не является долговременным хранилищем проекта. Данные, которые должны пережить invocation/deploy, обязаны сохраняться в утверждённом постоянном хранилище.

## 4. Правила изменения

1. P0 не изменяется in-place обработчиком. Создаётся производная копия.
2. P1 изменяется только новой версией/записью/forward-fix; история решений сохраняется.
3. Применённые database migrations не редактируются; исправление — новой forward migration.
4. Существенный производный материал после выдачи/публикации не должен молча менять содержимое под той же идентичностью версии.
5. Любая correction, влияющая на методику, торговую систему или каноническое обучение, требует teacher-authority и regression evidence в соответствии с действующей META/reliability архитектурой.
6. Новая версия не становится `stable`/`operational` только потому, что она новее. Требуется evidence gate.

## 5. Deletion Gate — обязательные условия автоматического удаления

Автоматическое удаление разрешено только если одновременно доказаны все применимые условия:

1. объект правильно классифицирован и не относится к защищённому P0;
2. объект больше не нужен активному процессу, restart/resume, rollback или предусмотренному recovery;
3. если объект должен сохраняться долговременно — существует постоянная копия в утверждённом хранилище;
4. постоянная копия фактически доступна;
5. её размер/идентичность и checksum проверены; для крупных/критических файлов предпочтителен round-trip verification;
6. location, checksum, provenance и verification зарегистрированы в Neon или другом каноническом реестре проекта;
7. удаление не ухудшает качество, воспроизводимость, скорость критического запуска, recovery, аудит или возможность расследовать ошибку;
8. для recovery/production rollback завершён требуемый observation period или создана и проверена замена;
9. действие удаления само оставляет audit record.

Если хотя бы одно обязательное условие не доказано или классификация сомнительна — не удалять.

## 6. Audit record удаления

Для автоматического удаления сохраняются минимум:
- идентификатор объекта;
- класс P0–P7;
- исходное местоположение;
- причина удаления;
- дата/время;
- исполнитель/процесс;
- постоянная копия или основание, почему копия не требуется;
- checksum/identity evidence, если применимо;
- правило/версия политики, разрешившая удаление.

Audit record хранится дольше удалённого технического объекта.

## 7. GitHub Actions retention

1. Пользовательские медиа и транскрипты не публикуются как Actions artifacts.
2. P4 progress/restart artifacts хранятся до завершения run и безопасной фиксации нужного milestone.
3. P2/P3 итоговые большие артефакты после завершения процесса копируются на Google Drive, проверяются и регистрируются; после этого GitHub retention уменьшается до минимально разумного срока.
4. Actions caches могут удаляться/истекать автоматически без Drive-копии, если это не блокирует критический recovery.
5. Нельзя использовать GitHub Actions как единственное долговременное хранилище незаменимого результата.

## 8. Failed experiments и ошибки

Неудачный эксперимент не обязан сохранять все временные гигабайты данных. Обязательно сохранить достаточно P1/P2 evidence, чтобы не повторить ошибку:
- версию/commit/run;
- параметры/контекст;
- root cause или установленный симптом;
- failure evidence;
- correction/regression case;
- итоговое решение: fixed/quarantined/rejected/unknown.

## 9. DDS milestone policy

Для DDS долговременными milestone являются как минимум подтверждённые этапы обучения/валидации, достаточные для воспроизводимости и продолжения процесса. Промежуточные shard states после успешной консолидации могут удаляться по Deletion Gate, если итоговый state содержит всё необходимое для resume/replay/audit.

## 10. Recovery override

Recovery-объекты и pre-promotion snapshots имеют специальную защиту. Их нельзя автоматически удалять только из-за появления нового release. Сначала новая линия должна пройти предусмотренные проверки, restore/recovery verification и observation period. После этого старый recovery может быть заменён новым проверенным recovery при сохранении audit trail.

## 11. Правило сомнения

Если система не может доказать безопасность удаления — объект считается необходимым и сохраняется.

Если система может безопасно освободить временное/дублирующее хранилище без ухудшения процессов — она должна предпочесть освобождение такого хранилища, а не бессрочное накопление копий.

## 12. Переходные действия

После принятия этой политики:
1. все workflows и архитектурные документы постепенно приводятся к P0–P7 и Deletion Gate;
2. старые абсолютные формулировки «ничего не удалять» помечаются как superseded этой политикой;
3. новые workflow обязаны явно задавать retention для крупных artifacts либо документировать, почему используется default;
4. для завершённых крупных артефактов при возможности выполняется Drive offload + checksum verification + Neon registration;
5. автоматическое физическое удаление из внешних систем включается только там, где существует технически доступный delete-action и он проходит Deletion Gate.
