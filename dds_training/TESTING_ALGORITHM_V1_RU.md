# Алгоритм тестирования DDS Learning v1

## 1. Назначение

Этот документ определяет, как проверяется программная и методическая часть
`dds-learning-v2.3` до запуска массового DDS-этапа.

Цель тестов — не получить зелёный значок любой ценой, а доказать одновременно:

- корректность бриджевой логики;
- корректность интеграции с локальным DDS3;
- отсутствие утечки между семействами сдач и holdout;
- воспроизводимость результатов;
- сохранность исходного кода и исторических фактов;
- невозможность случайного запуска массового обучения;
- полноту тестового покрытия или явное документирование пробелов.

Тестовый контур не меняет систему торговли школы и не запускает массовое
обучение.

## 2. Иерархия проверок

Тесты делятся на три уровня доказательности.

### 2.1. Чистая программная логика

Без DDS проверяются:

- PBN и частичные позиции;
- принадлежность карт;
- очередность хода;
- обязанность отвечать в масть;
- определение победителя взятки;
- семейная lineage;
- cross-fit folds;
- shards;
- калибровка;
- provenance;
- append-only ограничения;
- readiness и launch guards.

### 2.2. Реальный локальный DDS

После установки закреплённого DDS3 проверяются:

- пошаговая DD-траектория;
- нормализация значения на одну шкалу;
- DD-regret выбранной карты;
- равнооптимальные альтернативы;
- continuation-решения разыгрывающего и защиты;
- инварианты поворота стола и перестановки мастей.

Mock-ответ DDS не может заменить этот уровень.

### 2.3. Независимый решатель

На небольшой фиксированной выборке DD-таблицы DDS3 сравниваются с отдельно
скомпилированным независимым bridge-solver. Это не заменяет остальные тесты, но
проверяет, что вся система не согласилась с одной и той же ошибкой интеграции.

## 3. Канонический реестр тестов

Единственным реестром является `test_matrix.json`.

Для каждого теста фиксируются:

- уникальный `id`;
- файл;
- suite;
- timeout;
- один или несколько `PYTHONHASHSEED`;
- краткая цель.

Новый файл `*_selftest.py`, не добавленный в реестр и не имеющий явного
обоснованного исключения, блокирует CI. Это предотвращает ситуацию, когда тест
написан, но никогда не запускается.

## 4. Контракт покрытия

Каждый производственный Python-модуль в `dds_training` обязан иметь:

- ссылку хотя бы на один тест в `coverage.module_tests`; или
- временный waiver с конкретной причиной.

Количество waivers ограничено `coverage.max_waivers`. Увеличение лимита является
осознанным ухудшением тестового контракта и требует отдельного review.

Waiver не означает, что модуль проверен. Он означает только, что пробел видим и
не замаскирован зелёным CI.

## 5. Изоляция выполнения

Каждая тестовая программа запускается отдельным subprocess.

Для каждого запуска задаются:

- отдельные HOME и TMP;
- фиксированный `PYTHONHASHSEED`;
- UTC;
- фиксированная locale;
- `PYTHONDONTWRITEBYTECODE=1`;
- отдельный timeout;
- захват stdout и stderr.

Падение или зависание одного теста не скрывает результаты остальных. По
умолчанию runner собирает все ошибки, а не останавливается на первой.

## 6. Запрет оптимизированного Python

Исторические self-tests используют обычные `assert`.

Поэтому `python -O` и `python -OO` запрещены: при них Python удаляет assert и
может выдать ложный зелёный результат. Runner завершает работу до запуска тестов,
если `__debug__` выключен.

## 7. Детерминизм

Тест должен быть воспроизводимым при повторном запуске.

Для чувствительных участков используются несколько фиксированных hash seeds.
Это помогает обнаружить скрытую зависимость от порядка set/dict, не превращая
CI в невоспроизводимый случайный эксперимент.

Генераторы корпуса, folds, shards и выборки обязаны иметь фиксированные seeds и
проверяемые хеши.

## 8. Защита от самоповреждения

Тест считается проваленным, если после него изменился отслеживаемый исходный
файл в `dds_training`.

Smoke-workflow обязан быть read-only:

- `contents: read`;
- без `git commit`;
- без `git push`;
- без удаления workflow;
- без автоматической правки канонического алгоритма.

Тест может создать временные данные только вне исходного дерева или в явно
игнорируемых runtime-каталогах.

## 9. Fast и DDS suites

### Fast

Запускается при pull request и push. Содержит чистую логику, SQLite-контракты,
методические gates, lineage, калибровку, shards и архитектурные проверки.

Fast suite должна быстро давать полный список ошибок без сборки DDS.

### DDS

Запускается после установки локального DDS3. Содержит реальные solver-backed
проверки и независимый cross-check.

DDS suite не повторяет fast suite без причины. Разделение уменьшает время до
первой полезной ошибки и не допускает skip-cascade после одного раннего сбоя.

## 10. Отчётность

Runner создаёт JSON-отчёт `dds-test-report-v1`, содержащий:

- версию Python;
- SHA-256 test manifest;
- выбранные suites и test IDs;
- статус каждого invocation;
- hash seed;
- длительность;
- timeout;
- return code;
- stdout/stderr;
- обнаруженные изменения исходного дерева;
- итоговые счётчики.

CI сохраняет отчёты как artifacts. Зелёный workflow без доступного тестового
отчёта не является достаточным доказательством для массового этапа.

## 11. Негативные проверки

Обязательны тесты, которые доказывают не только успешный путь, но и блокировку:

- незаконной карты;
- revoke;
- неверного следующего игрока;
- неверной стороны решения;
- orphan self-test;
- duplicate test ID;
- отсутствующего покрытия;
- зависшего теста;
- изменения исходного дерева;
- holdout leakage;
- открытия sealed test без разрешения;
- смешивания sealed test с TRAIN;
- запуска этапа без двойного подтверждения.

Тест самого runner обязан намеренно создавать pass, fail, timeout и mutation и
проверять их правильную классификацию.

## 12. Критерии приёмки изменения

Изменение тестового или производственного алгоритма принимается, когда:

1. test manifest остаётся полным;
2. coverage contract выполнен;
3. fast suite зелёная;
4. при зависимости от DDS зелёная DDS suite;
5. независимый solver cross-check не обнаружил расхождений;
6. tracked source tree не изменён тестами;
7. machine-readable reports сохранены;
8. не было массовых DDS-результатов;
9. readiness и holdout gates находятся в ожидаемом состоянии;
10. новые пробелы не скрыты увеличением waiver budget без объяснения.

## 13. Канонические команды

Проверка реестра без запуска тестов:

```bash
python test_runner.py --manifest test_matrix.json --check-only
```

Fast suite:

```bash
python test_runner.py \
  --manifest test_matrix.json \
  --suite fast \
  --report /tmp/dds-test-report-fast.json
```

DDS suite после `bootstrap_linux.sh`:

```bash
source .venv/bin/activate
python test_runner.py \
  --manifest test_matrix.json \
  --suite dds \
  --report /tmp/dds-test-report-dds.json
```

Один тест:

```bash
python test_runner.py --manifest test_matrix.json --test crossfit
```

## 14. Граница доказательств

Зелёные тесты доказывают корректность проверенных контрактов. Они не доказывают
автоматически приобретённый бриджевый навык.

Для статуса `confirmed/stable` по-прежнему нужны реальные независимые transfer,
контрпримеры, regression streak и турнирные данные. Тестовый алгоритм только не
позволяет подменить эти доказательства программным успехом.
