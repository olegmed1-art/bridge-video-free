# DDS3 Analysis Algorithm v2.0

Дата версии: **2026-08-21**  
Статус: канонический алгоритм вычислительного DDS3-слоя «Школы спортивного бриджа».

Эта версия заменяет прежнее упрощённое представление «полная сдача → DD table». Она фиксирует уже работающие full-deal и position runtime, all-legal-moves/regret, persistent `SolverContext`/TT и более строгий evidence/regression protocol.

## 0. Неподменяемые правила

1. Все численные double-dummy значения, помеченные как DDS3, должны быть фактически вычислены каноническим DDS3.
2. Нельзя использовать модель, эвристику, web solver, классический DDS или иной анализатор как fallback для DDS3.
3. Если DDS3 недоступен или вход невалиден — DDS-зависимая операция прекращается fail closed.
4. DDS3 не исправляет сомнительные карты «по смыслу» и не реконструирует отсутствующие факты бриджевым рассуждением.
5. DDS3 вычисляет факты позиции; торговые и педагогические правила из его чисел автоматически не выводятся.

## 1. Evidence / Input Gate

### 1.1 Полная сдача

Принять PBN или структурированные N/E/S/W и проверить:

- ровно четыре руки;
- по 13 карт в каждой;
- ровно 52 уникальные стандартные карты;
- масти S/H/D/C и допустимые ранги;
- dealer/vulnerability — если требуются для Par/метаданных.

Только после успешной валидации разрешён `dd_table`.

### 1.2 Произвольная позиция

Для `bridge_dds3_position/v1` проверить:

- остатки четырёх рук;
- отсутствие дубликатов;
- допустимый trump/NT и `first`;
- согласованность размеров остаточных рук с текущей взяткой;
- карты текущей взятки отсутствуют в остатках рук.

Проверка текущего состояния не заменяет доказательство полной истории розыгрыша. Если требуется установить, на каком ходу была допущена ошибка, нужен реальный card-by-card record.

### 1.3 Изображение

Raw image сначала проходит отдельный vision/extraction layer. DDS3 получает только структурированное наблюдение `bridge_dds3_screenshot_observation/v1` или batch `bridge_dds3_screenshot_batch/v1`.

Vision-неуверенность, конфликт метаданных или неполная колода должны приводить к rejection/уточнению, а не к догадке DDS3.

**Текущий gap:** production raw-image extractor и заполненный >=50 real-screenshot regression corpus ещё не завершены.

## 2. Baseline полного расклада

Для каждой принятой полной сдачи канонический DDS3 вычисляет:

`DD0 = table[5 strains x 4 declarers] + Par`

Фиксируются:

- 20 значений взяток;
- Par score;
- Par contracts;
- engine/version/operation;
- `input_validated=true`;
- `fallback_used=false`.

Этот baseline является точкой отсчёта для последующего анализа торговли и розыгрыша, но сам по себе не объясняет причину результата за столом.

## 3. Replay партии

Replay запускается **только при наличии фактической последовательности карт**.

После каждого сыгранного действия строится следующая валидная позиция:

`P0 -> P1 -> ... -> Pn`

Для каждой позиции DDS3 получает значение максимально достижимого результата для интересующей стороны/контракта:

`V0 -> V1 -> ... -> Vn`

Если card-by-card record отсутствует, нельзя придумывать позицию ошибки. Допустим только анализ доступных фактов: контракт, declarer, lead (если известен), итоговое число взяток, baseline DD/Par и другие реально записанные поля.

## 4. Все legal moves и regret

В каждой анализируемой позиции вызывается настоящий DDS3 `position_all_moves`, а не только запрос «лучшей карты».

Для каждого legal move сохраняются:

- карта;
- DDS3 tricks/value после этого хода;
- множество равнооптимальных ходов;
- `best_tricks`;
- `regret = best_tricks - move_tricks`;
- класс regret: `0`, `1`, `2+`.

Ход с `regret=0` не считается ошибкой, даже если он отличается от первого хода в списке DDS3. Это обязательное правило, предотвращающее ложные ошибки при нескольких равнооптимальных картах.

## 5. DD trajectory и damage

По `V0...Vn` определяются:

- **first swing** — первый фактический ход, изменивший максимально достижимый результат;
- последующие swings;
- временная потеря;
- восстановление после собственной/чужой последующей ошибки;
- compensated error — ошибка одной стороны, позже компенсированная ошибкой другой;
- **final unrecovered damage** — изменение DD-ценности, которое не было восстановлено к концу рассматриваемой линии.

Следует различать:

`first_swing != final_damage`

Первый swing отвечает на вопрос «где впервые изменилась теоретическая возможность», а final damage — «какая часть потери осталась невосстановленной».

## 6. Классификация для разбора турнира

DDS3 evidence разделяется минимум на три уровня:

### Торговля

Сравниваются фактически достигнутый контракт/сторона/результат с full-deal DD/Par. DDS3 не определяет сам по себе, какая заявка была методически правильной в системе ученика.

### Розыгрыш declarer

При наличии replay анализируются позиции declarer, all legal moves, regret, first swing и final damage.

### Защита

Аналогично анализируются реальные позиции защитников. Нельзя объявлять конкретную карту защитной ошибкой только из конечного результата сдачи.

Для учебного вывода поверх DDS3 evidence используются материалы и методика школы; если соответствующего правила в них нет, оно не добавляется автоматически.

## 7. Context / TT reuse

Для последовательных и ветвящихся позиций одной сдачи следует использовать persistent position worker с одним `SolverContext`.

Контрольные telemetry:

- `persistent_worker`;
- `worker_generation`;
- `worker_request_index`;
- `context_reused`;
- `nodes`;
- `previous_nodes`;
- `nodes_delta`.

Повторный запрос той же позиции с reuse обязан быть семантически эквивалентен первому: те же legal moves и те же DDS3 values. Контекст разрешён только как оптимизация; он не может менять ответ.

## 8. Regression / expert protocol

### 8.1 Канонический CI gate

Обязательные реальные проверки:

- pinned DDS3 build;
- deterministic golden deal;
- Board 16 regression;
- настоящий position worker;
- context/TT reuse;
- negative position validation;
- production runtime `/readyz`;
- HTTP `dd_table`;
- HTTP `position_all_moves`.

Mocks/unit tests проверяют контракт, parsing и normalization, но не заменяют реальное DDS3 вычисление.

### 8.2 Сравнение с классическим DDS 2.9.0

Классический DDS — только post-hoc regression/reference expert.

Строгий порядок:

`freeze input -> DDS3 -> freeze DDS3 SHA-256 -> DDS 2.9.0 -> compare`

Запрещено:

- запускать reference solver первым и затем подгонять DDS3;
- заменять несовпавший DDS3 ответ ответом DDS;
- использовать DDS 2.9.0 как fallback;
- называть совпадение двух версий полностью независимым доказательством, поскольку они имеют общую кодовую родословную.

### 8.3 Новые corpus-тесты

Для расширенной проверки следует использовать детерминированную генерацию:

`fixed seed -> generate legal PBN corpus -> freeze corpus hash -> DDS3 -> freeze outputs -> reference expert`

Seed, corpus SHA и DDS3 output SHA должны быть зафиксированы до открытия результатов reference solver.

## 9. Improvement loop

Версия v2.0 сохраняет ранее принятый цикл улучшений и уточняет его вычислительную часть:

`locked predictions / baseline`  
`-> DDS3 evidence на TRAIN`  
`-> card-level investigation`  
`-> изменение алгоритма`  
`-> golden + regression`  
`-> blind retest без подглядывания в HOLDOUT`  
`-> принятие или откат изменения`

Нельзя оптимизировать правило по HOLDOUT и затем считать тот же HOLDOUT независимой проверкой.

Для каждого нового вычислительного компонента должен быть отдельный проверяемый контракт/golden: legal moves, equal-optimal/regret, trajectory, damage, context reuse, image extraction.

## 10. Observability и ошибки

Минимальные категории наблюдаемости:

- `invalid_deal`;
- `vision_rejection`;
- `dds_unavailable`;
- `dds_failure`;
- `metadata_conflict`.

Нужно разделять качество **извлечения входа** и корректность **DDS3 вычисления**. Ошибка vision не должна записываться как ошибка DDS3 solver.

## 11. Tournament adapter — правила запуска

Tournament adapter может преобразовывать записи турнира в перечисленные выше контракты, но не меняет вычислительные правила DDS3.

Перед массовым разбором турнира:

1. пользователь явно разрешает запуск конкретного турнира;
2. фиксируются источник, event id, целевой игрок/пара и доступные поля;
3. данные сохраняются/нормализуются до DDS3 расчётов;
4. полные сдачи проходят baseline;
5. только сдачи с фактическим play record допускаются к точному replay/first-swing анализу;
6. результаты ранжируются по учебной значимости уже на уровне методики школы.

Наличие URL турнира само по себе **не является разрешением на запуск**.

## Версионирование

Изменение численной семантики, входного position contract, regret semantics, trajectory/damage semantics или evidence protocol требует повышения версии этого алгоритма. Документационное уточнение без изменения семантики может оформляться как v2.x patch/minor revision.
